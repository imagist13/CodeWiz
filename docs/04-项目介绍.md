# CodeWiz: 一个可以端到端交付全栈项目的「超级个体」

## 一、项目背景

### 1.1 为什么做 CodeWiz

2024-2025 年，大模型能力快速迭代，AI Coding 工具（Claude Code、Cursor、Windsurf 等）开始真正进入工程化实用阶段。然而现有工具存在几个核心割裂：

- **工具割裂**：每款工具只支持自己偏好的模型和生态，换一个模型就得换一套工作流
- **上下文割裂**：对话历史、项目记忆、助手人格分散在各个工具中，无法跨工具复用
- **交互割裂**：无法通过手机 IM（微信、飞书）随时远程操控 AI 助手
- **自动化割裂**：定时任务、批量处理能力缺失，AI 只能被动响应

CodeWiz 由此诞生：**一个统一的多模型 AI Agent 桌面客户端，让用户无论在电脑前还是远程，都能通过任何 IM 渠道，驱动 AI 完成端到端全栈项目交付。**

### 1.2 核心差异化定位

| 维度 | 传统 AI Coding 工具 | CodeWiz |
|------|---------------------|---------|
| 模型支持 | 仅单一或少量模型 | 20+ 提供商一键切换 |
| 远程控制 | 无 | 微信/飞书/Telegram/Discord/QQ |
| 记忆持久化 | 无或仅会话级 | 语义记忆跨会话跨项目 |
| 定时自动化 | 无 | Cron + Interval 两种调度 |
| 多渠道分发 | 无 | 同一回复同步推送到多 IM |
| 桌面客户端 | 部分有 | 三端全支持（macOS/Win/Linux） |

## 二、功能说明

### 目标一：多模型统一接入（Multi-Provider）

**目标**：打破模型壁垒，用户无需更换工具即可在不同模型之间切换，保持同一会话上下文。

**实现方案**：
- 统一 Runtime 抽象层（Native / Claude Code SDK / Python Agent 三种运行时）
- Provider Resolution Chain：请求 → Session 配置 → 全局设置 → Claude Code 配置，四级覆盖链
- 支持 20+ AI 提供商：Anthropic、OpenRouter、AWS Bedrock、Google Vertex、通义千问、Kimi、DeepSeek、MiniMax、Ollama 等

**细化拆解**：
- [x] Provider Catalog（1121 行，20+ 提供商协议）
- [x] API Key 安全管理（加密存储，支持多个账户）
- [x] 模型参数配置（temperature、max_tokens、thinking budget）
- [x] 推理控制（Low / Medium / High / Max + extended thinking）
- [x] 流式响应 + SSE 事件分发

### 目标二：跨渠道远程控制（Bridge System）

**目标**：用户通过微信、飞书、Telegram、Discord、QQ 等 IM 平台远程与 AI 对话，随时随地掌控项目进度。

**实现方案**：
- 适配器抽象层（`BaseChannelAdapter`），统一消息收发接口
- 跨渠道 Markdown 渲染（HTML / Embeds / Lark MD / 微信小程序卡片）
- 流式预览 + 自适应限流（Telegram 200ms，Discord 100ms）
- Per-Session 锁机制，防止多群并发消息乱序
- 权限审批异步链路（危险操作 → 用户点击 IM 按钮确认 → 继续/终止）

**细化拆解**：
- [x] Telegram Adapter（Telegram Bot API，MarkdownV2 渲染）
- [x] Discord Adapter（Embeds + Component，按钮交互）
- [x] 飞书 Lark Adapter（Lark MD + 卡片消息）
- [x] QQ Adapter（QQ Guild Bot API）
- [x] 微信企业号 Adapter（企业微信 API）
- [x] 流式响应跨渠道分发（SSE → 各渠道适配器）
- [x] 权限审批 Broker（pending 队列 + 超时自动降级）

### 目标三：会话记忆与知识管理（Memory + KB）

**目标**：AI 助手具备持久化记忆能力，能跨会话、跨项目学习和检索知识。

**实现方案**：
- 语义记忆存储（`codepilot-memory` MCP Server，无条件加载）
- 关键词感知的 Memory 加载（语义检索，O(1) 而非 O(n)）
- Assistant Workspace（`soul.md` 助手人格 / `user.md` 用户画像 / `claude.md` 项目规范 / `memory.md` 记忆文件）
- 知识库检索（中文分词 Nerve + 轻量全文搜索 MiniSearch）

### 目标四：Skill 生态与自动化（Skills + Scheduler）

**目标**：用户通过可复用的 Skill 扩展 AI 能力，通过定时任务实现自动化工作流。

**实现方案**：
- 5 个来源的 Skill 发现（项目级 / 用户级 / 跨 Agent 共享）
- 双执行模式：Inline（注入主对话） + Fork（隔离子 Agent）
- Skill Marketplace（`skills.sh` 浏览器安装）
- 定时任务调度器（SQLite 持久化，Cron + Interval 两种模式）

### 目标五：文件级回退与安全（Checkpoint / Rewind）

**目标**：对话过程中可随时撤销 AI 操作影响，将文件和对话状态恢复到之前某个时间点。

**实现方案**：
- In-Memory 文件快照（完全独立于 Git，保护会话前已有变更）
- FIFO 20 个 checkpoint 上限（内存与精度的工程权衡）
- 双路径 Rewind API（SDK 内置 / Native 自研快照系统）
- 自动 Rewind Point 发射（每条用户消息前创建）

## 三、L1 与 L2 成果完成演示

### L1 成果演示：多模型对话（Native Runtime）

**演示场景**：在同一会话中，先后使用 Claude 3.5 Sonnet、DeepSeek V3、Kimi V1.5 回答同一个技术问题，全程保持上下文连贯。

**技术链路**：
```
用户切换模型 → Runtime Registry 路由到新 Provider
→ 重新组装 9 层上下文 → 同一会话续接对话历史
→ 流式 SSE 返回 → 前端渲染
```

**关键代码路径**：
- `src/app/api/chat/route.ts`（1060 行主入口）
- `src/lib/context-assembler.ts`（9 层上下文组装）
- `src/lib/provider-catalog.ts`（20+ 提供商定义）

### L2 成果演示：Bridge 远程控制（Telegram 渠道）

**演示场景**：用户在 Telegram 中发送"帮我创建一个 React 组件"，AI 自动完成以下流程：

1. 用户在 Telegram 私聊机器人
2. 消息通过 Telegram Adapter 接收
3. Bridge System 创建独立会话
4. AI 流式生成代码，通过 Telegram Adapter 实时编辑消息展示进度
5. 完成后代码写入用户指定的工作区文件
6. 若涉及危险操作（删除文件），用户点击 Telegram 按钮审批
7. 执行完成后，结果通过 Telegram 卡片消息返回

**技术链路**：
```
Telegram Webhook → TelegramAdapter.receiveMessage()
→ BridgeManager.route() → 创建/路由 Session
→ Chat Orchestrator（9 层上下文 + MCP 加载）
→ streamText() → SSE 事件 → TelegramAdapter.sendStream()
→ StreamingPreviewState 缓冲 → updateMessage() 实时推送
→ 用户点击 Inline Keyboard → Permission Broker → Agent Loop
```

## 五、技术说明

### 核心技术架构

CodeWiz 采用 **Electron Shell + Next.js App Router** 的桌面应用架构：

```
┌────────────────────────────────────────────┐
│  Electron Shell（窗口/托盘/PTY/AutoUpdater）│
├────────────────────────────────────────────┤
│  Next.js App Router（React UI + API Routes）│
├────────────────────────────────────────────┤
│  Backend Core（Node.js）                    │
│  ├── Chat Orchestrator（会话编排）           │
│  ├── Context Assembler（9层上下文）         │
│  ├── Runtime Registry（3种运行时）           │
│  ├── MCP Loader（动态MCP服务器）             │
│  ├── Bridge Manager（多渠道适配器）          │
│  ├── File Checkpoint（快照/回退）           │
│  └── Skill Registry（技能发现与执行）        │
├────────────────────────────────────────────┤
│  SQLite（本地持久化 ~/.codepilot/）         │
└────────────────────────────────────────────┘
```

### 关键工程难点

详细方案见 [02-技术说明-关键工程难点.md](./02-技术说明-关键工程难点.md)，核心包括：

1. **上下文召回精度**：9 层上下文分层组装 + 双阈值压缩 + RowID 边界过滤
2. **跨栈类型一致性**：1326 行中央类型文件 + 穷举式 switch 防护
3. **Skill 热加载**：5 来源发现 + Per-cwd 缓存 + 双执行模式
4. **断点重放**：In-Memory 快照（非 Git）+ 双路径 Rewind API
5. **多渠道消息路由**：适配器抽象层 + 流式预览限流 + 权限审批 Broker

### 技术栈总览

| 层级 | 技术 |
|------|------|
| 前端框架 | Next.js 16 + React 19 + TypeScript 5 |
| 样式 | Tailwind CSS 4 + Radix UI + Motion |
| 桌面壳 | Electron + electron-builder |
| 终端 | node-pty + ConPTY |
| 数据库 | SQLite（better-sqlite3） |
| AI 运行时 | Vercel AI SDK / Claude Code SDK / Python Agent |
| AI 模型 | 20+ 提供商（Anthropic / OpenRouter / GLM / Kimi / DeepSeek / Ollama 等） |
| 扩展协议 | MCP (Model Context Protocol) |
| 国际化 | i18next + react-i18next |
| 桌面打包 | macOS DMG / Windows NSIS / Linux AppImage |
| CI/CD | Playwright（smoke/e2e/visual 测试） |

### 关键性能与质量指标

- **本地优先**：所有数据存储在 `~/.codepilot/`，无需任何云服务
- **零外部依赖**：无 Redis / 无 Memcached / 无 CDN / 无 Serverless
- **流式延迟**：Telegram 渠道推送间隔 200ms，Discord 100ms
- **上下文压缩**：80% 预压缩阈值 + 70% 兜底预算
- **Checkpoint 内存**：仅追踪会话修改文件，O(修改量) 而非 O(项目大小)
