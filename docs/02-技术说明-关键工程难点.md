# 技术说明 — 关键工程难点与解决方案

## 1. 上下文召回精度

### 问题背景

CodeWiz 面临的核心上下文问题：当对话历史持续增长时，如何确保模型始终能精准召回最相关的信息，同时不超过模型上下文窗口限制。

### 难点分析

**多层上下文叠加问题：** 系统需要同时处理 9 个不同来源的上下文层——从编译期的 Widget 系统提示，到会话级别的 Session Prompt，再到工作区 Identity 文件（soul.md/user.md/claude.md），以及动态的 Memory Hint、Assistant 指令、Dashboard 摘要、Skill 注入、斜杠命令和知识库检索。这些层级的优先级、有效性和相互覆盖关系极其复杂。

**Token 估算误差：** 使用 `estimateContextTokens()` 进行上下文预算，但估算值与模型实际 token 计数存在偏差。不同模型的编码方式（cl100k_base vs o200k_base）导致 token 计算不准确，可能出现"估算未超但实际超窗"的情况。

**已压缩消息的重复回填：** 使用 SQLite `rowid` 作为压缩边界标记，但若上下文组装逻辑未严格按 rowid 过滤，已被摘要的旧消息可能被重新喂入模型，造成信息冗余和预算浪费。

**动态上下文优先级：** 用户在对话中途切换工作目录或加载新项目时，已组装好的静态上下文片段可能与当前工作区不再相关，但系统无法自动失效缓存。

### 解决方案

**分层组装策略（Context Assembler）：** 将 9 层上下文严格分为两类——Static Parts（1-3 层，编译期或会话创建时确定，用于 Prompt Cache）和 Volatile Parts（4-9 层，每轮动态组装）。通过分离静态/动态边界，最大化利用 LLM 的 Prompt Cache 机制，减少每次请求的 token 传输量。

```typescript
// src/lib/context-assembler.ts
const allParts = [...staticParts, ...volatileParts].filter(Boolean);
return {
  systemPrompt: allParts.join('\n\n'),
  // 静态部分变化少，天然适配 prompt cache
};
```

**双阈值压缩机制：** 设置 80% 预压缩阈值和 70% 兜底预算。当估算 token 超过 80% 窗口时，触发自动压缩，保留最近 50% 窗口的消息用于摘要，其余压缩到 `context_summary`。压缩完成后重新计算 fallback budget，确保下一轮对话有足够空间。

**RowID 边界过滤：** 压缩操作记录压缩后的最新 `rowid` 作为边界。后续上下文组装时，通过 `WHERE _rowid <= ?` 严格过滤已压缩消息，确保同一段对话只被喂给模型一次（作为摘要）。

**关键词感知的 Memory 加载：** 不做全量历史加载，而是通过 `codepilot_memory_search` MCP 工具进行语义检索，仅加载与当前 prompt 相关度最高的记忆片段。这将内存召回从 O(n) 降为 O(1)——只加载最相关的几条。

## 2. 跨栈类型一致性

### 问题背景

CodeWiz 是一个真正的前后端同构 TypeScript 项目：前端（React/Next.js）与后端（Node.js API Routes）共享同一套类型定义。但两者运行环境不同（浏览器 vs Node.js），且存在 Electron 桌面层（独立进程），三方之间的类型传递容易出现不一致。

### 难点分析

**SSE 事件类型的双向契约：** `/api/chat` 返回的 SSE 事件类型（17 种）既是服务端序列化格式，也是前端解析契约。任何新增事件类型或修改字段结构，都需要同步修改两处。类型不安全的手动 JSON 序列化/反序列化容易引入运行时错误。

**MessageContentBlock 多态联合类型：** 定义了 5 种内容块类型（text/thinking/tool_use/tool_result/code），前端渲染层需要穷举所有类型做 switch-case 分发。遗漏任一类型会导致编译通过但运行时渲染错误。

**Agent Loop 的外部类型依赖：** Native Runtime 的 `AgentLoopOptions` 依赖 Vercel AI SDK 的类型，但 SDK 类型与自研的 Runtime Interface 存在概念差异（如 `streamText` 的 tool 格式 vs 自定义 tool result 格式）。两个类型体系的映射逻辑分散在代码中，容易出现不对齐。

**Electron IPC 的类型盲区：** preload 脚本暴露的 `window.electronAPI` 是手动定义的接口，与主进程实际暴露的 API 可能不一致。TypeScript 无法在编译时验证 Electron IPC 通道两端的类型匹配。

**数据库 schema 与 TypeScript 类型脱钩：** SQLite 表结构用 SQL 定义，TypeScript 类型用手写 interface 定义。两者之间没有自动化校验机制。添加一个 nullable 字段容易遗漏更新 TS 类型，反之亦然。

### 解决方案

**中央类型文件（src/types/index.ts）：** 所有跨栈共享的类型集中在一个 1326 行的文件中，作为唯一真实数据源。前端组件和后端 API 路由都从该文件导入，避免类型分散导致的版本不一致。

```typescript
// src/types/index.ts — 1326 lines
export interface ChatSession { ... }
export interface Message { ... }
export type MessageContentBlock =
  | { type: 'text'; text: string }
  | { type: 'thinking'; thinking: string }
  | { type: 'tool_use'; id: string; name: string; input: unknown }
  | { type: 'tool_result'; tool_use_id: string; content: string; is_error?: boolean }
  | { type: 'code'; language: string; code: string };
export type SSEEventType = 'text' | 'thinking' | 'tool_use' | 'tool_result' | 'status' | 'result' | ...;
```

**穷举式 switch 防护：** 前端渲染层对所有 `MessageContentBlock` 类型做穷举分发，遗漏类型在编译期报错。结合 TypeScript 5.5+ 的穷举联合类型检查，确保每种内容块都有对应的 UI 渲染逻辑。

```typescript
// 前端消息渲染
function renderBlock(block: MessageContentBlock) {
  switch (block.type) {
    case 'text': return <TextBlock text={block.text} />;
    case 'thinking': return <ThinkingBlock thinking={block.thinking} />;
    case 'tool_use': return <ToolUseBlock name={block.name} input={block.input} />;
    case 'tool_result': return <ToolResultBlock content={block.content} />;
    case 'code': return <CodeBlock language={block.language} code={block.code} />;
  }
}
```

**自研 Runtime 类型隔离：** 在 `src/lib/runtime/types.ts` 中定义了完整的 `AgentRuntime` 接口和 `RuntimeStreamOptions`，将运行时抽象与 SDK 内部类型解耦。Native Runtime 自己实现类型映射逻辑，不依赖 SDK 的类型体系。

```typescript
// src/lib/runtime/types.ts
export interface AgentRuntime {
  readonly id: string;
  readonly displayName: string;
  readonly description: string;
  stream(options: RuntimeStreamOptions): ReadableStream<string>;
  interrupt(sessionId: string): void;
  isAvailable(): boolean;
  dispose(): void;
}
```

**ConversationRegistry 的全局会话注册：** 使用 `globalThis` 模式注册会话，确保 Next.js 热更新后会话状态不丢失。同时通过类型化的 `Query` 接口封装 SDK 会话对象，对外不暴露 SDK 内部类型。

```typescript
// src/lib/conversation-registry.ts
export function registerConversation(sessionId: string, conversation: Query): void
export function getConversation(sessionId: string): Query | undefined
```

**Electron 类型对齐脚本：** 通过 `preload.ts` 导出的 API 与 `main.ts` 暴露的 API 保持严格的 1:1 对应关系，所有 IPC 通道的 handler 在两侧都有类型签名。preload 使用 `contextBridge.exposeInMainWorld` 暴露类型化接口。

## 3. Skill 注册热加载

### 问题背景

CodeWiz 支持从 5 个不同目录发现 Skills，且 Skills 可以跨工作区、跨用户、跨 Agent 共享。用户在日常使用中会持续安装/卸载/编辑 Skills，但服务端进程（Next.js）不会自动感知这些文件系统变更。

### 难点分析

**多目录增量发现问题：** 5 个来源目录的 Skills 可能重名（如两个目录都有 `git-commit.md`），需要合理的优先级和去重策略。扫描所有目录的开销不可忽视（尤其涉及 `os.homedir()` 和网络挂载目录）。

**文件变更感知延迟：** Next.js 的服务端进程是长期运行的，文件系统的变更不会自动触发 Skill 缓存失效。用户在编辑器中修改了一个 Skill 文件，但 API 返回的仍是缓存中的旧版本。

**Skill 格式兼容性：** Skill 文件格式（YAML frontmatter + Markdown body）需要被正确解析。格式错误的 Skill（如缺少必需字段）应该被优雅地跳过而不是崩溃整个发现流程。

**Skill 与 MCP Server 的联动：** 部分 Skills 的执行依赖于特定的 MCP Server 配置。动态加载 Skill 时，需要同时确保关联的 MCP Server 也被正确初始化。

**跨 Agent 的 Skill 作用域：** `~/.agents/skills` 目录下的 Skills 理论上可被多个 Agent 共享，但实际使用时需要控制哪些 Agent 可以访问哪些 Skill，防止权限泄露。

### 解决方案

**目录优先级链：** 严格按优先级从高到低扫描，返回第一个匹配名称的 Skill 定义：

```typescript
// src/lib/skill-discovery.ts
const SKILL_DIRS = [
  '.claude/skills',         // 项目级 → 最高优先级
  '.claude/commands',      // 项目斜杠命令
  path.join(os.homedir(), '.claude', 'skills'),   // 用户级
  path.join(os.homedir(), '.claude', 'commands'), // 用户命令
  path.join(os.homedir(), '.agents', 'skills'),  // 跨 Agent → 最低优先级
];
```

**Per-Working-Directory 缓存：** 缓存 key 为 `cwd`（当前工作目录），切换项目时自动失效。手动 `invalidateSkillCache()` 供需要强制刷新的场景（如 Skill 编辑器保存后）。

```typescript
// src/lib/skill-discovery.ts
let cachedSkills: SkillDefinition[] | null = null;
let cacheWorkingDir: string | null = null;

export function invalidateSkillCache(): void {
  cachedSkills = null;
  cacheWorkingDir = null;
}
```

**YAML Frontmatter 解析 + 防御性容错：** 使用 `skill-parser.ts` 解析 frontmatter，对于格式错误或缺少必需字段（name、description、allowedTools）的文件，记录警告并跳过而非抛出异常。

```typescript
// src/lib/skill-parser.ts
export interface SkillDefinition {
  name: string;
  description: string;
  body: string;
  allowedTools: string[]; // 必需，否则跳过
  whenToUse?: string;
  context: 'inline' | 'fork';
  arguments: SkillArgument[];
  model?: string;
  effort?: string;
  userInvocable: boolean;
  filePath: string;
}
```

**内联与分叉双执行模式：** Skill 执行时分两种模式——`inline` 将 skill body 注入到主对话流中（共享上下文），`fork` 启动一个子 Agent 并限制其可用工具集（隔离执行）。

```typescript
// src/lib/skill-executor.ts
switch (skill.context) {
  case 'inline':   // 追加到当前 conversation 的 system prompt
  case 'fork':     // runAgentLoop() with restricted tool set
}
```

**Skill Marketplace 版本锁定：** 安装 marketplace Skills 时写入 `skills.lock.json`，记录版本信息。卸载时从 lock 文件移除。安装和卸载都是原子操作，确保 Skill 集合状态始终可追踪。

## 4. 断点重放（Checkpoint / Rewind）

### 问题背景

CodeWiz 需要支持对话过程中的"回退"功能：用户可以撤销最近 N 轮 AI 操作的影响，将文件和对话状态恢复到之前某个时间点。这要求系统精确追踪文件变更历史，并能在任意checkpoint点精确还原。

### 难点分析

**会话前已有变更的保护：** 用户在启动 CodeWiz 会话前，可能已有未提交的本地文件变更。回退机制必须只撤销会话期间引入的变更，不能触及会话前的任何文件内容。

**In-Memory 快照的内存压力：** 每个 checkpoint 存储所有修改文件的完整快照内容。对于大型项目（如 node_modules），快照会消耗大量内存。需要对快照大小进行合理限制。

**SQLite 消息截断的一致性：** 回退时需要同时处理两层状态：对话历史（SQLite）和文件状态（文件系统）。截断 SQLite 消息相对简单，但配合文件系统回退时存在一致性问题——若文件回退成功但 SQLite 截断失败，会导致状态不一致。

**SDK Session 与 Native Runtime 的回退路径差异：** Claude Code SDK 有自己的 `conversation.rewindFiles()` 方法，而 Native Runtime 完全没有会话概念，需要完全依赖自定义的 checkpoint 系统。两条路径的抽象层必须对上层（Rewind API）保持一致。

**Checkpoint 与 Git 的关系：** 不使用 `git checkout HEAD` 意味着完全依赖自研的快照系统。这虽然保护了会话前变更，但也意味着如果用户在会话期间同时使用 git 操作，checkpoint 系统和 git 分支可能产生冲突。

### 解决方案

**In-Memory 文件快照（非 Git）：** 所有文件快照存储在内存 Map 中，完全独立于 Git 状态：

```typescript
// src/lib/file-checkpoint.ts
interface FileSnapshot {
  content: string;
  createdAt: number;
}
interface Checkpoint {
  messageId: string;
  sessionId: string;
  modifiedFiles: string[];         // 仅追踪会话中修改过的文件
  snapshots: Map<string, FileSnapshot>; // key: 相对于 cwd 的路径
  createdAt: number;
}
```

**仅追踪 modifiedFiles：** `recordFileModification()` 仅在文件被 Agent 首次写入时记录该文件路径。之后每次 `createCheckpoint()` 只快照这些已被记录的文件，而非整个工作区。这将内存消耗从 O(项目总大小) 降低到 O(会话修改量)。

**FIFO 限制：** 每个会话最多 20 个 checkpoint，超过后自动淘汰最旧的。这是内存使用量和回退精度之间的工程权衡。

**双路径 Rewind API：** Rewind 端点根据运行时类型选择不同路径，对上层保持统一接口：

```typescript
// src/app/api/chat/rewind/route.ts
if (runtime === 'sdk') {
  await conversation.rewindFiles(messageId); // SDK 内置方法
} else {
  // 1. 截断 SQLite 消息到 rewind point
  // 2. restoreCheckpoint() 从快照恢复文件
  // 3. 重新组装上下文
  truncateMessages(sessionId, targetRowid);
  restoreCheckpoint(sessionId, messageId, cwd);
  reassembleContext();
}
```

**Rewind Point 自动发射：** 在 `agent-loop.ts` 中，每条用户消息前自动创建 checkpoint 并通过 SSE 发送 `rewind_point` 事件。这确保用户可以回退到任意用户消息点，无需手动触发。

```typescript
// src/lib/agent-loop.ts
if (!autoTrigger) {
  const lastDbUserMsg = [...dbMessages].reverse().find(m => m.role === 'user');
  controller.enqueue(formatSSE({
    type: 'rewind_point',
    data: JSON.stringify({ userMessageId: rewindMessageId }),
  }));
  createCheckpoint(sessionId, rewindMessageId, workingDirectory);
}
```

## 5. 多渠道消息路由（Bridge System）

### 问题背景

CodeWiz 的 Bridge 系统允许用户通过 Telegram、Discord、飞书、QQ、微信等多个 IM 平台与 AI 对话。每个平台的消息格式、API 能力、限制各不相同，需要统一的抽象层来管理。

### 难点分析

**消息格式差异：** Telegram 支持 MarkdownV2，Discord 使用 embeds，飞书使用 Lark MD，不同平台的渲染能力差异巨大。同一份 AI 回复需要在多个渠道上正确呈现。

**流式响应的跨渠道分发：** AI 回复通过 SSE 流式返回，但不同 IM 平台的推送机制不同：Telegram 是轮询 + 编辑消息，Discord 是 Webhook 追加编辑，飞书是卡片流式更新。需要将同一个流同步到多个渠道的适配器。

**并发会话隔离：** 同一 Telegram Bot 可能同时接收多个群/私聊的消息，每个对话需要独立的会话上下文。消息路由必须正确匹配 sender → session。

**平台 API 限制：** Telegram 消息有 4096 字符限制，Discord embed 有字段长度限制，飞书卡片有节点数量限制。长回复必须被正确截断或拆分成多条消息。

**权限审批的异步链路：** Agent 执行危险操作时需要用户审批。在 IM 渠道中，用户通过点击按钮（inline keyboard）批准/拒绝。这需要维护一个 pending 权限队列，并在超时后自动降级。

### 解决方案

**适配器抽象层：** 所有渠道适配器实现统一的 `BaseChannelAdapter` 接口：

```typescript
// src/lib/bridge/types.ts
export interface BaseChannelAdapter {
  readonly channelType: ChannelType;
  readonly adapterId: string;
  connect(): Promise<void>;
  disconnect(): Promise<void>;
  sendMessage(ctx: OutboundContext, message: OutboundMessage): Promise<SendResult>;
  sendStream(ctx: OutboundContext, stream: ReadableStream<string>): Promise<void>;
  sendPermissionRequest(ctx: OutboundContext, req: PermissionRequestEvent): Promise<void>;
  updateMessage(ctx: OutboundContext, messageId: string, content: string): Promise<void>;
}
```

**跨渠道 Markdown 渲染：** 每种渠道有独立的 Markdown 渲染器，将统一的内容块转换为平台特定格式：

| 渠道 | 渲染器 | 格式 |
|------|--------|------|
| Telegram | `markdown/telegram.ts` | HTML（parse_mode=HTML） |
| Discord | `markdown/discord.ts` | Embeds + Component |
| 飞书 | `markdown/feishu.ts` | Lark MD + 卡片 |
| 基础 | `markdown/render.ts` | 中间 IR 表示 |

**流式预览 + 自适应限流：** 对于流式响应，Bridge 使用 `StreamingPreviewState` 在内存中缓冲 token，周期性地将预览文本通过 `updateMessage` 推送更新到 IM 渠道。同时对更新频率做限制（Telegram 200ms，Discord 100ms），防止触发 rate limit。

**Per-Session 锁机制：** 每个 Bridge session 有独立的文件锁（`lockKey = `bridge:${channelType}:${chatId}`），确保同一渠道会话的并发消息被串行处理，防止消息乱序。

**Permission Broker：** 危险操作的权限请求通过 `permission-broker.ts` 转发到对应渠道，生成带按钮的交互消息。用户点击后，结果通过内部事件总线传回 Agent Loop，解除 pending 状态并继续或终止执行流。
